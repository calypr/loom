# Loom HTTP operations and backend ownership

**Decision:** remove the retired aggregate scheduler first. Consolidate the duplicate receipt authorization rules as a separate high-priority unit. Two smaller units remove a discarded project-view read and the JSON conversion inside the selection-member loop. All four changes fit behind the existing API. The strongest public API candidate is the Viewer's faceted page read; it needs an experiment before a cutover decision.

**Coverage at `932d28b05`.** 61 distinct path templates, 66 method/path pairs (45 POST, 16 GET, four PUT, one DELETE). A Fiber probe constructed the production HTTP server, called `registerRoutes`, normalized path parameters, and compared `GetRoutes(true)` with operations from `loomapi.GetSwagger()`. Both settings of `ClickHouseEnabled` yielded 66 mounted, zero missing, zero extra. The probe used injected services. It proves registration, not successful execution of every operation against real databases. The production registrar installs the same strict handler in both configurations; available dependencies affect responses. Request ID, recovery, logging and authentication middleware precede the generated handlers. Each public operation below links to its handwritten handler on the audited branch.

## Implementation results

- **Aggregate scheduler.** The HTTP service now resolves the materialization and read scope once, executes the ordered jobs as one reader batch, and returns normalized results. The mounted-route test sends two equivalent named jobs in reverse name order and verifies two sorted results from one SQL statement. Four tests that constructed the retired scheduler were removed. After SQL work succeeds, the handler checks for cancellation before building the response. The old result-channel select could choose either readiness event.
- **Receipt policy.** Four executable-receipt rules now have one implementation in [support/receipt.go](../internal/explorer/lifecycle/support/receipt.go). Validation inputs, error stages, call order, and caller-specific execution bindings are preserved.
- **Project views.** Adoption, defaults, config save, and delete now use write-only helpers. The service still authorizes the state before the write and authorizes fresh state afterward. A saved-config fixture covers the remaining reads, stale catalog, foreign catalog, post-write denial, and mapped post-write read failure. Both post-write failures leave exactly one write for that request.
- **Selection pages.** A direct member mapper preserves JSON for all four combinations of optional fields. A 100-member benchmark including page encoding measured 1,517 → 204 allocations and about 211 KB → 26 KB per page. The three Go benchmark samples on an Apple M1 Max ran at 278–313 µs before and 42–44 µs after. This isolates page conversion and response encoding from persistence, HTTP, and UI.
- **Route wiring.** A private typed dependency struct replaces the variadic list. The parity test now uses the production registrar for both ClickHouse modes. The recipe-execution test drives the mounted HTTP endpoint and verifies an authorized response and foreign-project concealment.

The implementation commits are `9cd1002bc` (aggregates and routing), `b0d78f02a` (receipts), `b12a1284e` (project views), and `bbdaf6746` (selection). Three independent `gpt-6.1-sol` reviewers checked the final diffs for result/error ordering and route setup, receipt predicates and callers, and mutation authorization plus selection JSON. Focused tests passed. No reproduced review finding remained.

Verification on the final Go source at `bbdaf6746` passed `make test-go`, `make lint-go-comments`, `make test-integration`, and the standalone ClickHouse aggregate integration test. The integration runner reported 42 successful profiles, identical before/after source fingerprints and successful cleanup. Its six explicitly unverified cases require opt-in CDA, profiling, or provisioned corpus settings. The earlier integration attempts exposed a missing test database and then a changed test-source fingerprint. The passing rerun initialized the owned database and used the committed Go source. Logs are in `/private/tmp/loom-operation-audit-go-staged.log`, `/private/tmp/loom-operation-audit-integration-pinned.log`, `/private/tmp/loom-arango-integration-55613/summary.json`, and `/private/tmp/loom-operation-audit-clickhouse-pinned.log`.

`make lint-filenames` still flags the tracked `arango_stream.go`, `clickhouse_stream.go`, and `output_stream.go` in dataframe execution. The baseline contains all three names and this change leaves those paths alone.

The two handlers keep their own failure text and imported-source eligibility. Row definition still uses the active-revision fallback in `PreviewWorkspace`. ## Backend architecture cycle decisions

- **Proposal preparation** now owns the shared draft checks for column policy and source relationship. The scope recheck is required at compile time. The first slice also compared row definition, population removal, and construction and records their distinct loading and execution rules above.
- **Workspace validation errors** use one validation-code mapping in lifecycle support. Compile, reconcile, construction, and publication still choose their original public stage. Construction calls the receipt output validator directly.
- **Viewer rows and facets** keep the separate endpoints and current identity check. Reopen the combined-read candidate with paired browser requests against the same active data release, including a release turnover and a facet-only failure. Count catalog reads and query calls and compare client latency. The synthetic service-level benchmark below did not establish a performance case.
- **Arango error normalization** remains split by use case. To test a classifier move, inject the same wrapped cancellation, deadline, and forbidden errors in the general dataframe query, saved preview, and recipe publication query paths. Compare HTTP status, public error code and stage, and the wrapped cause at each boundary. Move the mapping only if that comparison shows how to preserve all four.
- **Recipe execution authorization** stays on the common record reader. REST concealment and Explorer's requirement for usable execution and output states serve different callers.
- **Construction façade and proposal execution** keep the current service owners. Construction selection routes already share the underlying search implementation. Construction, choice, and population-member proposals already share the preview executor. A proposed façade change needs to remove call-site or constructor plumbing across these consumers while preserving the different input contracts.
- **Explorer affordances** continue to distinguish deleting a saved view config from deleting an Explorer. The latter is gated off and needs a product decision before a public route is added.
- **JSON response conversions** keep the measured typed mapper on selection pages. Before changing other shapes, test the same production-sized response with its existing codec and a typed mapper. Compare bytes for optional fields and payload variants and measure allocations and CPU. The selection measurement alone cannot establish equivalence for other shapes.

## Ranked implementation units

### 1. Remove the retired GraphQL resolver scheduler and retain SQL job batching

The Viewer calls `queryOutput` in [api.ts](../ui/packages/loom-ui/src/api.ts). A faceted read sends **one** POST containing all requested specs to the aggregations route. The old GraphQL resolver installed an operation context with the expected number of root aggregate fields. Its caller was removed in `83d70d30a` (reproduce with `git log -p -S 'dataframes.WithOperationContext' -- '*.go'`). Today the only production installation of the private context key is inside the uncalled installer. With that state absent, every live `submitAggregateCall` dispatches a singleton synchronously. The dormant per-operation dataset cache needs the same key. The REST handler calls only the rich aggregate method. Renaming both exported methods `WithOperationContext` and `AggregateInput` in a scratch Go overlay and running `go build ./...` succeeded. Declaration searches, history, the private context key and the successful compile supply independent checks.

**Current:** HTTP → rich call object → result channel → singleton dispatch → selector/materialization grouping maps → job batch → per-call demultiplex. **Target:** `AggregationsInput(ctx, input)` resolves access and materialization once, converts specs to ordered jobs, calls `published.Reader.ExecuteAggregateBatch` once and checks job errors in request order and normalizes successful results by name. Delete the legacy HTTP service entry, queue, timer, goroutine, cancellation fan-out, grouping by caller and operation-scoped cache from [aggregates.go](../internal/api/dataframe/dataframe/aggregates.go) and [service.go](../internal/api/dataframe/dataframe/service.go). Check direct users of published legacy job modes separately. The lower-level reader still supports callers and fixtures that use those modes.

**Why the distinction matters:** the rich-shape test executes three logical jobs in two statements. The wider reader fixture executes 158 logical jobs in one statement. Both passed with the counting query adapter. Keep the shared SQL planner, self-filter removal, names/order, job-local errors, empty/over-limit rejection, cancellation and existing reader-error precedence. Re-run `TestPublishedDataframeREST`, `TestExecuteAggregateBatchRichShapesShareScans`, `TestAggregatePlanCombines156CountFacets` and the owned ClickHouse integration. Retire only scheduler tests whose production mechanism disappears. Compare rows-only and mixed-facet Viewer requests on the same materialization; record statements, returned data and latency. No latency improvement was measured in this audit.

### 2. Make one implementation own executable receipt policy

Cell trace and row lineage explain the same receipt-backed output through different execution queries. Following both routes uncovered **two implementations of the same authorization and binding rules**. [Cell trace](../internal/explorer/lifecycle/trace.go), authoring preview and artifact reads use the definitions in [authoringcore/policy.go](../internal/explorer/authoringcore/policy.go). Row lineage, row comparisons and population mapping use [lifecycle/support/rowdef.go](../internal/explorer/lifecycle/support/rowdef.go). Comparing the definitions after removing only the package qualifier yields identical code for four functions: `ValidateAuthorizedReceiptExecution`, `ValidateReceiptOutputContract`, `ReceiptHasOutput` and `ApplyAuthorizedScope`. They cover receipt project/generation/schema/scope checks, output membership and execution binding. A future policy change otherwise has two owners.

**Implement:** keep the support definitions already used by rowdef and population, group them in a receipt-named file there, migrate all four authoringcore names and delete their duplicate bodies. Both paths already depend on support. A Go overlay performed this substitution across ten files, including the one test calling the old name. The Explorer subtree and Explorer HTTP package passed on the overlay (32 packages with tests, eight without). Preserve separate request validators, stage names, error mapping, column checks and caller-selected inclusion of the auth resource path. No query, authorization lookup or cache changes are required. Re-run `go test ./internal/explorer/... ./internal/api/explorer` and the owned trace/preview/publication integration checks. Future consolidation of trace orchestration is a separate question. This unit already gives four sensitive rules a single implementation.

### 3. Give project-view mutations one owner for the response read

[Mutation orchestration](../internal/explorer/projectconfig/mutation.go) checks authorized state, calls an inner write method, discards the state it returns, then reads and checks state again. Four [inner methods](../internal/explorer/projectconfig/service.go) each call `ViewBuilderState` after writing. This affects adoption, defaults, config save and config deletion. The first and last access checks serve different purposes. The middle snapshot is discarded without an access check.

| Counting repository, successful service call | Settings reads | Owner lists | State access checks | Writes |
|---|---:|---:|---:|---:|
| Save defaults or delete config, current | 3 | 3 | 2 | 1 |
| Same calls, inner read removed | 2 | 2 | 2 | 1 |

The overlay drove actual service methods with a counting repository. On an injected write error both variants performed one settings read, one list, one access check and one write attempt, returning the mapped storage error. The measured cases used empty owner lists. A populated project also resolves referenced revisions; the experiment makes no timing claim for that workload.

**Implementation:** make the four inner write helpers private and have them return `error`; keep request decoding after pre-authorization, expected revision/version checks, actor, adoption's per-execution checks, and final response authorization. The repository methods with similar names have different contracts. Migrate the direct projectconfig service tests to the public mutation entry point. Verify a pre-check denial, a write conflict, a post-write store read failure (same public status and redaction), and loss of execution access between the two checks. A post-write failure must never cause an automatic second write. Compare success responses for all four operations and measure the two remaining state reads on a populated project. Run `go test ./internal/explorer/projectconfig ./internal/api/explorer -run 'ViewBuilder|Catalog'` and the owned storage integration.

### 4. Replace per-member JSON encoding in selection pages

[readSelection](../internal/api/explorer/selection.go) calls `directAuthoringJSON[loomapi.SelectionMember](member)` once per member. The helper marshals to bytes and immediately parses those bytes into a second Go struct. The generated ref has four string fields; the other two member fields are optional. Use a typed transport mapper that copies the ref and sets ordinal/member-key pointers only when the domain value would be emitted. Keep the generated response type at the HTTP boundary.

A scratch comparison sent both outputs to the same escaping sink. With both optional fields absent, allocations per converted member fell from 13 to 0. With both present, they fell from 15 to 2. Marshaling the generated result produced identical bytes in both cases. This measures Go allocations in the conversion alone. Verify independent presence/absence of each field, empty/nonempty pages, cursor, error responses and actual page allocation counts before landing. There are 46 production calls to the generic converter, including custom command payloads; this finding covers the selection loop only. Run the selection and Explorer handler tests and check the public response against existing fixtures.

Implement and verify each unit separately. Unit 1 changes the dataframe HTTP service. Unit 2 changes shared receipt policy call sites. Unit 3 changes the view mutation implementation. Unit 4 changes selection response conversion. None needs a wire migration. Preserve response/error contracts and run the focused checks above plus the repository Go suite and comment lint on the implementation branch.

### Combined Viewer read experiment

A disposable prototype resolved the materialization and access once before starting the existing row and aggregate readers concurrently. The counting fixture reduced materialization lookups from two to one, kept the same two ClickHouse calls and peak concurrency of two, and returned byte-identical results. With a publication turnover injected between lookups, the separate calls observed different execution IDs and the combined call observed one. A canceled context made zero SQL calls.

The live loopback ClickHouse fixture had 20,000 synthetic rows, 500 distinct facet values, a 100-row page and one terms facet. Both designs returned the same data. Across seven interleaved warm service-level calls each, median latency was **12.68 ms** for separate reads and **13.43 ms** for shared resolution. The first separate and combined calls took 17.25 ms and 11.64 ms respectively. These first calls shared a server and ran in that order, so the cold figures cannot compare cold performance. The fixture used an in-memory catalog, bypassed HTTP and the UI, and did not measure live authorization or remote network costs. The warm result provides no performance case for changing the public API. Keep the two routes and the Viewer's identity check. Reopen only with a production representative workload that measures the omitted costs or a product requirement for same-materialization consistency.
