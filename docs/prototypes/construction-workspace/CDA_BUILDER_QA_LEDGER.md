# CDA Builder browser QA ledger

This ledger tracks the visible Builder in the single local CDA stack. **Pass** means the stated browser path has evidence. **Partial** means one or more required checks are missing. A feature is complete only when its controls, CDA values, Apply, reload, edit or remove, and restoration pass where those actions apply. API success alone does not count.

The browser driver is [`scripts/verify-cda-builder.mjs`](../../../scripts/verify-cda-builder.mjs). Local DOM and network evidence is retained under `.artifacts/cda-builder/`. The earlier action inventory and evidence paths are in `.audit/cda-builder-qa/coverage.tsv`. These local evidence files are not checked in.

## Performance gate added to the active goal

For each new dataframe-building feature, measure the elapsed time from a valid user edit or Preview click until its CDA rows render in the browser. A preview taking more than **5 seconds** is a feature failure: profile the frontend and backend path, improve the owning bottleneck on the loaded CDA dataset, and rerun the same browser case. Record both proposal and rendered-row timing when an operation has two preview stages. Keep routine checks bounded, but include representative CDA cardinalities for performance work; do not treat a fast one-record selection as proof that a feature scales.

Grouped Pivot hillclimb: on 742,505 Specimen records, the previous 25-row preview scanned every index entry, grouped about 100,000 keys, and peaked near 614 MB. Reordering index fields and forcing a sorted collect did not materially improve the 3.54–3.59-second database profile, so neither change was retained. A two-phase query prototype selected the same 25 ordered groups in 0.55 seconds and fetched all 275 contributors in 0.37 seconds, with an 18 MB peak in the group-selection phase. The accepted implementation runs both scans in one AQL statement and keeps canonical cell policies. Its full-CDA browser median is 3.725 seconds, versus the prior 4.13–4.14-second warm proposal; the Arango parity test covers two group keys and missing/null values. A live proposal completed in 3.757 seconds while 100 ms sampling showed Arango container anonymous memory rising by 469 MB at peak and returning near baseline; this includes other Arango activity and is not an isolated AQL query peak. The next Pivot hillclimb profiled the actual two-scan query. A bounded diagnostic copy used 277 KB of AQL and 1,396 plan nodes; Arango spent 2.912 seconds optimizing the plan and 0.740 seconds executing it. A preview-only renderer now binds category specifications once and runs one category loop. On the same full-CDA Specimen browser case, three current-code proposals took 1.896, 1.892, and 1.893 seconds (median 1.893), versus 3.725 seconds before. The first browser run took 1.888 seconds. A successful full-CDA Observation SUM Pivot took 1.663 seconds; its 25 visible rows matched the independent CDA aggregation and survived Apply, reload, edit, removal, and restoration. The focused Arango parity test matched static full execution for SUM, MIN, MAX, duplicate contributors, and NULL categories. A separate index-order experiment improved the warm preview only to 3.54 seconds while making first use take 6.59 seconds, so its code and exact generated index were removed. Construction source projection does not currently support a distinct MISSING Pivot category; that existing limitation remains outside this performance change. A fresh full-CDA Specimen category discovery found 136 values in 1.847 seconds click-to-DOM, with 1.671 seconds in the API. A single diagnostic Arango profile scanned 742,505 index entries and spent 1.439 seconds executing; it was not retained as a standalone artifact. No speculative index change was kept.
