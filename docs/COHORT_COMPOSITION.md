# Cohort composition

## Problem and usage

A user who has filtered source records must be able to select a saved cohort and continue building the dataframe. Existing source filters continue to select member records. Later filters and operations consume cohort rows. Preview, Cancel, Apply, removal, reload and publication retain pinned memberships and stable identities.

The current path translates Document.Rows and Construction independently, rejects their coexistence in recipe validation, and then bypasses construction lowering for GroupRows. Removing the UI/backend guards alone silently skips authored operations.

## Shape

Persist the cohort insertion anchor in Document.Rows.Groups; Rows remains the single owner of the pinned revision and policy. A missing anchor denotes source projection. Choosing cohorts captures the preceding authored step as anchor. Compilation validates that exact anchor and materializes one compiler-owned COHORT_GROUP stage there, between the preserved construction prefix and subsequent authored steps.

The typed stage consumes compiler-proven root contributors, not arbitrary constructed row IDs. Earlier Group/Pivot stages retain their root contributor sets when required. Pinned definitions form the left side, preserving empty cohorts and overlapping memberships. Member values use only authorized contributors that survive the prefix. Unassigned classification and ERROR policy use the pinned source selection, independently of prefix filtering. Filtered assigned records cannot become unassigned.

The stage retains complete revision/selection guards, scope and membership digests, project/generation/resource boundaries, authorization, deterministic ordering and {group_revision_id, group_id} row identity. Subsequent stages use ordinary typed sequence lowering/rendering and stage capabilities.

Recipe and authoring validation must validate the effective sequence, including the compiler-owned cohort boundary, while keeping arbitrary stage references invalid. Lifecycle proposal receipts still permit only the intended row-definition change; callers do not coordinate storage queries or filter rewrites.

## Synthesis decision

Two read-only design candidates traced source replacement and contributor grouping. Both concluded that replacement alone changes scalar source-filter meaning into group-filter meaning. The contributor grouping candidate is the base; the replacement candidate contributes retaining all existing revision/source guards and a typed source/stage contract. No operation-specific filter pushdown or ban-only change is accepted.

## Type sketch

- GroupedRows.AfterStepID: persisted exact predecessor anchor, default source projection.
- SemanticGroupRows carries that anchor and pinned revision/value intent.
- PhysicalStageCohortGroupOp and PhysicalStageCohortGroup payload: revision bindings, policies, contributor input and multiplicity, member reductions, output identity.
- lowerCohortGroupStage: validate provenance, create typed schema/descriptor and physical payload.
- renderCohortGroupStage: guarded pinned definitions plus eligible contributor intersection, then standard stage continuation.

Names may be refined during implementation; behavior and ownership are the contract. Prefer one coherent materialization boundary over parallel special pipelines.
