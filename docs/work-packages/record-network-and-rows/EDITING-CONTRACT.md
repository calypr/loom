## Owner and switching rules

`RecipeEditingIdentity` binds project, Explorer, output, snapshot token, draft
version and digest. `RecipeEditTarget` distinguishes an existing occurrence,
source step, column or operation from a new connection or appended operation.
An operation target includes its input stage. Inspection and presentation state
are outside this owner: switching Record network / Define a row / both does not
start, cancel, save or retarget a proposal.

| State | Permitted behavior |
| --- | --- |
| saved | Begin one mutation; read either representation |
| editing | Edit the selected fact; another mutation requires Apply or Cancel |
| previewing | Show loading; only the current request token may supply candidate data; Cancel revokes it |
| preview-ready | Show proposed semantics and receipt-bound result together; Apply only this candidate, or Cancel |
| applying | Disable conflicting mutations and Cancel until acknowledgement; complete only the owning command |
| failed | Saved recipe unchanged, candidate authorization cleared; retry this edit or Cancel |
| stale | Changed table/draft/snapshot revokes candidate authorization, preserves an explicit old-edit notice and blocks Apply; Cancel then recover against current identity |

Table selection remains available during a proposal. Changing the table or draft
puts the earlier edit in a visible stale state and clears its candidate authorization.
Cancel the earlier edit before starting another mutation; returning to its table
does not restore Apply.
Callbacks retained before Cancel, another Preview, or a table/draft switch are
ignored. No interface switch alone discards an edit.

## Authoritative candidate projection

Source-relationship/source-step proposals return the exact verified candidate
Document, AuthoringNetwork and RowIdentityPlan from their receipt workspace.
The proposal envelope binds these facts to the same output and base identity.
The saved-network endpoint must not label its result as proposed state.
Construction proposals already return complete validated candidateConstruction;
combine it with the unchanged saved source document for display only. The
complete construction and validated stage descriptors remain authoritative.
`projectRecipeCandidate` returns no projection when neither source candidate nor
validated construction is available. Such a UI must explicitly say the proposed
semantics are unavailable, rather than presenting saved semantics as proposed.

Both editors receive the same selected DraftTable and saved/proposed label.
Graph-first and row-first supported actions therefore invoke identical typed
operations. Generated IDs may differ between independent creation runs; compare
canonical occurrence paths, policies, input scope and ordered operation meaning.
Within one saved recipe, preserve every occurrence, column and operation identity.

For literal subject S1 with observations O1=7 and O2=9, a saved ALL column has
`[7, 9]` on S1. RELATED_EXPAND creates `(S1,O1)` and `(S1,O2)` and keeps that
same column `[7, 9]` on both rows. A separately authored matched-record scalar
column may produce 7 and 9. Requiring a match is a third operation: it excludes
unmatched source rows and retains the ALL policy without creating pairs.
Group uses its complete key tuple; it never fabricates a resource occurrence.

Focused owner and lifecycle-adapter tests establish ownership/projection
boundaries. Full graph-first, row-first, mixed, exact-value, persistence and native
layout acceptance remains ticket 07's integrated verification obligation.

Root READY assessments expose only the verified target document, network and row
identity from the existing scoped preview receipt. They do not claim a full
persisted-workspace digest. Existing consumer and shared-filter consequences stay
visible, and Apply uses the exact reviewed root proposal through the existing
command. Imported preserve-root changes remain blocked; explicit replacement
projects the detached candidate before confirmation.

Accepted legacy columns without a stable column ID remain intact in the document.
The network omits unidentified bindings instead of inventing IDs or provenance.
Their saved policies remain readable in the row expression; the new stable-ID
policy proposal is unavailable, with the existing source settings still accessible.
